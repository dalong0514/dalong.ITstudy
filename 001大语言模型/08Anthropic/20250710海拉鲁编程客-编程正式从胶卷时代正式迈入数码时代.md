### 01

在讲 Cloud Code 的技巧之前，我们先聊一聊编辑器是怎么进化的。我们把时间退回到 2000 年，我大概是从 2015 年开始编程的。在那个时候，我写代码主要靠手打，偶尔会用代码片段补全。那时的补全很简单，比如写一个有 name 和 age 属性的 user 对象，当你敲「user.」的时候，编辑器会自动弹出 name 和 age 让你选。这是最早的代码补全，手敲代码、补全、代码复制粘贴是常态。

2018 年，Tabnine 诞生了，它能补全整行代码，还能理解你想写什么函数，这在当时可算一个大的突破。而 Tabnine 背后的模型是 GPT-2，做 GPT-2 的 OpenAI，四年后将会彻底地改变这个世界。

2022 年，变革开始加速。到了年底，ChatGPT 更是引爆了整个科技圈。2023 年初 GPT-4 发布，那叫一个震撼！我记得当时的感觉是，不少场景下，这玩意儿写的代码比我写得好多了。那段时间我天天干什么呢？就是把代码复制粘贴到

近些年，AI 编程经历了几个阶段的演变。起初，开发者们在 ChatGPT 中让 AI 优化代码，再粘贴回来，来回倒腾，戏称自己是「代码倒爷」—— 不生产代码，只是代码的搬运工。到了 2024 年，AI 已经入驻各类编辑器，让开发者可以随时调用，无需再进行复制粘贴。而进入 2025 年，AI 编程工具更是「神仙打架」，它们不仅能补全代码，还能理解整个项目、洞悉开发意图，并帮助拆解复杂的任务。以 Cursor 为例，当我需要一个落地页时，它能立刻理解需求，识别我的代码风格，并一气呵成地创建文件、编写代码。此时，AI 已不再是简单的工具，而是一个真正的编程伙伴。

无论是 Cloud Code、Cursor，还是其他 Agentic Coding 工具，它们都在重新定义我们编写代码的方式。「智能体编程」听起来很酷，但其实可以用四个字来概括：编程伙伴。你的 AI 编程伙伴就像真人一样，能够感知代码库、理解你的需求、制定计划并自主编码。

但问题来了：Cloud Code 功能如此强大，为什么偏偏选用了一个「黑框」（终端界面）？我查阅资料、观看访谈后，找到了两个主要原因：

第一，编辑器的碎片化问题。在 Anthropic 内部，开发者使用的编辑器五花八门，包括 VSCode、Vim、Emacs 和 IntelliJ。如果只支持某一个编辑器，其他人就无法使用。

第二，UI（用户界面）成为了 AI 最大的枷锁。许多工具都在追求漂亮的界面、丰富的插件和独立的应用程序，但大家慢慢会发现一个致命问题：UI 限制了 AI 的能力。回顾 Agentic Coding 的核心循环 —— 感知、规划、行动，你会发现它与界面是否漂亮毫无关系。华丽的界面和复杂的交互反而成了负担，而极致简约的终端却是一种返璞归真。

终端界面有三大优势：

1、自由度最大：AI 可以调用一切系统能力，不受 UI 框架的限制。

2、认知负担最小：用户只需说明「我想要什么」，无需学习复杂的操作界面。

3、工具链天然融合：Git、npm、Docker 等所有开发工具本来就是基于命令行的。

不要觉得这是倒退，恰恰相反，这是返璞归真。当然，很多人吐槽 Cloud Code 界面简陋，我承认漂亮的界面的确能让人心情愉悦。但我个人体验下来，Cloud Code 在理解代码的能力上，要远超其他同类工具。很多人觉得终端难用，是因为没有尝到效率的甜头；一旦尝到，你就会觉得 UI 漂亮与否并不重要。

除此之外，Cloud Code 还有一个最大的「杀手锏」—— Token 额度。它给的额度简直像不要钱一样。如果折算成 API 调用，我一天就能「烧掉」价值一两百美元的 Token，可见其额度之慷慨。

### 02

接下来，我们讲一讲 Cloud Code 的使用技巧。

我将分享一些我认为最有用的技巧，这些技巧可以按照我的「谋、定、动」三字诀来划分，即「谋定而后动」。用自动驾驶来类比，你就能更好地理解：

「谋」就是把需求聊透，就像开车前要确定目的地，例如是从河南新乡到山东德州，而不是从纽约到德州。

「定」是规划清晰的路线，像导航一样把每个关键路线和节点都标记好。

「动」就是要快速执行。路线清晰了，就可以「油门踩到底」，当然不要超速，同时也要注意观察路况，如果路线不对要及时调整方向盘，避免跑偏。

下面我们展开讲解。

第一步：「谋」—— 把需求聊透，将需求文档化。

首先，为什么要这样做？因为你需要通过与 AI 的反复沟通，来确保自己的思路清晰，并让 AI 完全理解你的意图。紧接着，让 AI 复述一遍你的需求，以确保你的理解和 AI 的理解完全对齐。这样，如果后续执行出错，你就能快速定位问题是出在理解层面还是执行层面。

这里有一些小技巧可以分享：

1、首先，要切换到 Opus 模型，因为它处理复杂需求时更可靠。

2、接着，我会用手机在备忘录中输入我的需求，例如：「我需要实现支付功能，请你帮我完成。功能包括订单支付、通知会员购买。需要支持支付宝、微信支付、银行卡支付。核心功能要实现一个支付订单，并处理支付管理状态、支付回调、支付查询、退款（包括选择性退款或关闭退款）以及对账功能。」

这个阶段之所以如此重要，原因有二：第一，确保我们自己的思路是清晰的；第二，在与 AI 反复沟通的过程中，它可能会发现我们逻辑上的一些漏洞。当需求被系统化地整理好之后，后期出现问题也能快速回溯。将需求聊透，可以降低 80% 的返工率。

第二步：「定」—— 确定任务，拆解计划。

需求聊透之后，就需要对任务进行拆分，这是非常关键的一步。我会让 Claude Code 把所有步骤列出来，通常会这样说：「基于这份需求文档，请你帮我制定一个执行计划，标明哪些任务可以做、哪些任务可以并行，形成一个渐进式的方案。」

第三步：「动」—— 快速执行。

计划制定好后，就可以进入「动」的环节了。因为前面已经沟通得非常透彻，所以在第三步，我就可以让 Claude Code 开启「狂飙模式」，这时候不要犹豫，把速度拉满。有 Git 作为保障，即使出了问题也可以回滚。

有时候，Claude Code 在全速执行过程中会出错，该如何解决呢？

一种方法是直接「踩刹车」，按下 `ESC` 键中断任务，然后重新输入你的需求。

另一种方法是，如果偏离得不远，你只需要继续输入一些微小的补充指令，Claude Code 就能识别并在下一个步骤中帮你调整。

此外，当 Claude Code 执行的任务多了，有时候会显得「不太聪明」，这时可以输入 `clear` 命令清除它的短期记忆。

还记得我们之前做的需求文档（To-do list）吗？我们可以引用这个文档，然后输入「继续执行」并回车，它就会先读取这份文档，然后接着执行。

补充技巧：

三字诀讲完了，我们再补充一些小技巧。使用 `init` 命令可以快速扫描项目，形成一个初步的项目结构认知。

Cloud Code 会记住文档的每次操作，并将常用命令记录下来，例如如何启动前端、如何编译后端、如何查看错误日志等。请注意，要善用注释，因为注释是给 Cloud Code 阅读的，而非给人类阅读的。

有些人可能会怀念 Cursor 的 Apply/Reject 方案，你可以在对应的 IDE 或编辑器中安装相应插件，选中代码片段进行调整。当然，就我个人而言，大部分情况下我无需选中代码，直接通过口头描述即可。

Cloud Code 还有一些快捷操作。例如，你可以在输入框中输入「你帮我提交代码，生成规范的 commit message」，也可以直接输入「commit」。如果有人不希望 Cloud 在代码中署名，可以在 settings 中设置一个参数，这样代码就都归属于你了。

在编写动画效果时，我沉淀了一些修复布局、制作动画和添加标签的命令。这些命令较长，每次输入都相当耗时，因此我建议创建自定义命令。如果某个提示词我已经使用了三四次，且每次都需要输入较长的文本，我就会创建一个自定义命令。另外，如果你是新手，想写项目，建议使用一些现成的脚手架，这可以帮你省去大量时间。

### 03

聊完了 Cloud Code 的一些技巧，我们再来谈谈提示词技巧。首先要明确，我讲的是提示词技巧，而非提示词工程技巧。那些复杂的提示词工程技巧需要让工程师去研究，我们普通用户只需记住一点：把话说清楚。经常有人问我是否需要套用某种提示词框架，答案是完全不需要。你只需专注于把任务描述清楚，简单反而更好，因为 Cloud Code 已经足够聪明，一些复杂的框架反而可能会对它产生误导。

这里要分享一个有意思的现象。我不知道你们是否对 AI 发过脾气，比如情急之下说一句「你给我好好想想」，结果 AI 突然就变得更聪明了。这不是玄学，在 Cloud 中，这是实打实的技术。Extended Thinking（扩展思考）功能能让 AI 进入深度思考模式。我觉得 Cloud Code 里面似乎藏着几个「魔法咒语」，比如 Think、Think Hard、Think Harder、Ultra Think。为什么当你说「你给我好好想想」时会突然奏效？因为它可能调用了「Think Harder」这个指令。AI 思考得越久，答案往往越准确，就像人一样，深思熟虑总比脱口而出更可靠。

深度思考对于一些复杂任务非常有必要。例如，当你要求它「详细分析这个支付模块的瓶颈，并给出重构方案」，并使用「Ultra Think」时，你可能会发现服务器不停地超时。这时，你需要搭配下一个技巧使用，即「分步思考」。让 AI 将复杂问题自行尝试拆解。

支付功能可能会被拆解为：理解业务系统、对接支付渠道、设计订单状态机、实现核心逻辑以及进行异常处理。搭配链式思考后，UltraThink 将很少超时。

接下来的技巧是，在编写提示词时，应尽量使用正面表达，即告诉 AI 要做什么，而非不要做什么。这就像教育孩子，如果过多地限制「这不能做，那不能做」，反而会束缚他们，让他们不知所措。

反面案例是：「不要使用 any 类型」、「不要写重复代码」、「不要忘记错误处理」。

正面案例则是：「请使用明确的 TypeScript 类型」、「将公共逻辑提取为函数」、「增加 try-catch 进行错误处理」。

可以看到，正面表达能让 AI 明确方向，而不是处处设防。

当你需要生产级别的代码时，请提前说明标准。例如：「你需要实现一个通用的缓存系统，要求是：适用于所有合法的输入，而非仅针对测试用例；不要硬编码，要实现真正的逻辑；代码需保证健壮、可维护、可扩展。如果需求不合理，请直接告诉我。」这样做，能在一定程度上降低 AI 为了应付测试而投机取巧的可能性。

还有一个关于长文本优化的技巧：内容在前，指令在后。如果要粘贴很长的错误日志或文档，记住这个法则：先把日志或文档贴上去，然后输入指令，例如「基于以上错误日志，帮我分析崩溃的原因并提供修复方案」。将大段文本放在前面，指令放在后面，AI 的理解效果会好很多，这是由模型架构决定的。

### 04

我们来聊一聊 AI 编程的边界在哪里。我将其总结为三个核心要素：大模型、工程和人。

首先是大模型。大模型决定了 AI 编程的天花板。简单来说，如果连 Claude、CodeGemma 2.5 Pro 这类顶级模型都写不出的代码，那么当前的 AI 编程就无法实现。这就像再优秀的赛车手，也不可能让普通轿车跑出 F1 的速度，模型能力是硬性限制。

其次是工程。工程是让模型能力落地的外壳。Claude Code、Cursor、Copilot 这类工具，本质上都是大模型的套壳，其作用是优化交互体验、管理上下文，并将其集成到开发流程中。但工具再好，也无法突破底层模型的限制。Claude Code 作为套壳层，做得比较好的一点是缩短了人与大模型之间的距离，即你下达指令后，它会尽量帮你把一切做好。当然，像 Cursor Code 也做得不错。

第三是人，也就是工程师。工程师在 AI 编程中扮演三个关键角色：

1、定义者：只有清晰地描述需求，AI 才能准确输出。

2、把关者：负责审核代码质量、业务逻辑和性能表现。

3、创新者：并非所有需求和代码都已被 AI 充分训练，一些关键的架构设计和算法创新，仍然需要人类的创造力。

目前，AI 编程模型能够胜任的是一些常规功能的实现、代码的重构、测试与文档的生成。理解其三要素，就能更理性地看待 AI 编程：模型有多强，能力就有多强；工具有多好，体验就有多好；人有多专业，结果就有多专业。AI 编程并非要替代程序员，而是成为了程序员的超级助手。认清 AI 的边界，才能更好地使用它。

几天前，我的 AI 编程助手突然宕机了。那个下午，我被迫手动编写代码。没有 AI 的辅助，手指在键盘上犹豫不决，大脑疯狂运转，却总觉得少了点什么。一个简单的功能，以前用 AI 编程助手可能 10 分钟就能搞定，现在却磕磕绊绊地写了 20 多分钟。这并非说语法记不清楚，而是整个编程习惯都变了 —— 我已经习惯于描述需求，而不是从零开始实现细节。更让我震惊的是，当我写完代码，第一反应居然是想让 AI 助手帮我检查一下。

这一刻，我突然明白了，我们可能正在经历编程界的「从胶卷到数码」的革命。还记得胶卷时代吗？摄影师每按一次快门都要深思熟虑，36 张底片张张珍贵，构图、光圈、快门全在脑中运筹。暗房冲洗，一步错则步步错，没有删除重拍，只有一次机会。

到了数码时代，摄影变了。存储卡管够，可以随意创作、即拍即看、不停迭代。核心技能变成了审美和眼光，后期处理也成了必修课。

编程的变革好像也是这样。传统程序员像胶卷摄影师，每行代码都需深思熟虑，Bug 靠经验和直觉定位，底层的原理必须烂熟于心。而 AI 时代的程序员更像是数码摄影师，AI 可以快速生成多个方案版本，「择其善者而从之，其不善者而改之」，通过实时验证进行快速迭代。核心能力变成了识别好代码的能力，而提示词则成了基本功。

别误会，我不是说基础不重要了。就像摄影师依然需要懂光影、懂构图一样，程序员依然需要理解核心原理。但是，我们创作的方式、思考的路径、解决问题的手段，都已经彻底改变了。

那个下午，我有点失落，也有点激动。失落的是，时代变了，我们回不去了。激动的是，身处这样一个时代，我们不必回去。

好，今天的节目到此为止，我是海拉鲁编程客，AI 永不眠，我们下期节目再见，拜拜。
