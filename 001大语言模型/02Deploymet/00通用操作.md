阳老师曾提到一个很有意思的观点：在很多情况下，我们人类的能力确实无法完全吸收所谓「全局」的所有信息。此时，可以用最精华的 20% 来代表其余的 80%。这与我们在《聪明的阅读者》（或其他相关课程 / 书籍）中提到的抽样阅读类似，即通过阅读最核心、最精华的内容来理解整个领域。因为我们知道信息的分布规律 —— 这一点在课程中也曾提及 —— 所以可以运用此方法。

### 03

那么，我们就先进入本期必修作业的讲解。我先讲讲关于必修作业，我的一个思路。我们的作业是挑选一个期刊或者会议，去下载其所有的论文。虽然这里我们作业的要求……

关于高被引论文数据的处理，我发现许多人确实倾向于直接依据高被引排名来筛选数据。例如，在使用 Web of Science（通常简称为 WoS）这类数据库时，用户可以直接勾选排名前 1000 篇的高被引论文进行下载。虽然这种方法看似缩小了数据收集范围，但实际上它有悖于我们建立全局数据认知的原则。

原因在于，假设您现在勾选并下载了当前被引量排名前 1000 的论文。那么一两年后，当您需要更新数据时，这前 1000 篇论文的名单很可能已经发生了变化。届时，您难道要重新下载一遍吗？如果重新下载，新数据如何与旧数据进行合并与查重？更重要的是，您可能已经在旧数据上添加了许多笔记和资料，这些既有成果如何在新旧数据整合时得到保留？在仅有新下载的部分高被引数据时，您将难以分辨哪些是新增的文献，哪些是原有的。因此，这种看似直接的做法（或许是按照某些作业要求执行的）其实存在一个「小陷阱」，长远来看并非最佳实践。

更佳的方式是：如果您选择从 WoS（Web of Science）这类数据库下载数据，应当将某一特定来源（例如，某个您关注的期刊，如 IEEE 旗下的期刊）的全部论文数据完整下载下来。之后，您可以利用各种工具或插件 —— 目前市面上有许多插件支持此功能 —— 来分析本地数据库中论文的被引数据，并直接在 Zotero 等文献管理软件内部生成被引数据排行。然后，您可以从这个完整的、已排序的本地数据集中筛选出前 1000 篇高被引论文，并将它们放入一个新建的专属文件夹中，以此来满足特定的作业要求或研究需求。

这样做的好处在于您保留了完整的原始数据集。将来如需增补数据，可以直接在原始数据的基础上进行操作。您可以根据时间节点进行划分。例如，若当前数据是截至今年 9 月下载的，那么在下次更新时，您可以设定检索条件（或编写一个表达式），仅下载自上次数据收集截止日期（例如去年 9 月）至今的新增文献，从而避免重复下载已有的旧数据。然后，将这批新下载的数据导入到您已有的、包含该期刊（或来源）全部论文的完整数据库中。接着，对整个合并后的数据集重新进行被引次数排行更新。这样一来，您就不会破坏那些已经做过笔记和标记的原始文献记录。

因此，这种方式能够更好地保留原始数据，为我们后续的数据操作和分析提供了更大的灵活性和空间。这也正是阳老师一直强调的「保留一份原始数据」的原则，同时也是「实体分离」概念在文献管理实践中的具体应用。

综上所述，直接下载部分高被引论文的做法存在一个「陷阱」，建议大家尽可能避免。此外，关于文献数据的获取，大家可能习惯于使用 Zotero 配合 WoS 进行下载，接下来我还想介绍一种新的方式……

Web of Science（WOS）数据库的数据可能不够全面，此外，其下载过程也十分繁琐。例如，下载某一期刊的文献时，有过操作经验的同学应该了解，需要不断更换关键词，逐页勾选并翻页。并且，由于是国外网站，数据传输速率较慢，有时甚至会发生服务器宕机，导致需要从头开始，非常麻烦。

因此，我向大家推荐一个非常实用的数据库，名为 OpenAlex。这个名字可能与我们的 Alex 同学、Alex 助教或 Alex 教练有所重合。该数据库是一个开源的学术数据库，其数据量相对更为丰富。我们知道，WOS 和 Scopus 等数据库各有其擅长的领域。OpenAlex 的一个特点是数据量较大。虽然其部分元数据可能不够完整，但我们的重点在于，收集的论文越多越好。因为收集的文献越多，意味着我们能获得更全面的认识，从而减少信息遗漏。后续如果需要增补摘要等其他非关键元素，可以使用其他插件来完成。但最重要的元素是 DOI（数字对象标识符），我们应尽可能多地收集。

需要注意的是，在 Web of Science（WoS）等其他数据库中，我看到有些文献的最高被引次数可能达到 35,000 次。不同数据库的数据可能存在差异。因此，最好不要将从一个数据库获得的被引数量与其他数据库进行比较，因为它们获取被引数据的信息来源可能完全不同。所以，不同数据库之间的绝对数值最好不要直接对比，但其文献的相对排序，即使不看具体数量，也基本是一致的。例如，我看到有同学截图显示，在 WoS 数据库中排名第一的论文是《Faster R-CNN》，这篇论文在我们的数据库中（指通过 OpenAlex 获取并导入 Zotero 的数据）排名也是第一。大家可以进行简单的交叉验证。

获取其他元数据，例如被引数量，非常方便。而且，正如我刚才提到的，这个数据库不仅可以获取论文，还可以获取作者信息。因此，我们的必修内容有两个主要任务：一是将高被引论文导入并获取其 PDF（稍后会对此进行介绍）；二是保存关键学者的维基百科页面和个人主页。

这种方法其实可以使用 OpenAlex，通过编写好的代码快速实现，甚至可以一键生成。因为 OpenAlex 可以直接获取作者信息。我们可以看到，它能直接获取特定作者的信息，不仅能获取作者的维基百科链接，此处可能做了简化，展示的信息较少。例如，这里显示了作者姓名、ORCID（一个作者的唯一标识符网站，通过它可以获取许多信息）。它还提供了一些很有用的数据，例如 WorksCount，即该作者发表的作品数量，比如这位作者可能有 195 篇作品；以及他的总被引数量，即这 195 篇作品的总引用次数，这位作者的引用次数可能达到一万次。此外，还有其所属机构等信息。

有了这些元数据，保存下来会非常方便。并且可以通过代码批量获取这些关键信息，而不必像之前那样需要逐个复制作者名字再去查找维基百科。当获取某个作者信息时，例如，它也会提供其主页链接，甚至包括作者的照片。主页链接中不仅包含个人主页，还可能包括维基百科链接、谷歌学术主页等。这非常方便。此处不作详细展开，大家后续可以自行探索使用。

另一个议题是如何批量获取论文的 PDF。针对这一点，可以给大家介绍一个小技巧，即利用 GitHub 上的小工具。当大家想要实现某个特定功能，或希望在 GitHub 中寻找能完成某项操作的工具时，可以直接去 GitHub 进行搜索。

首先，我们可以在 GitHub 等平台上进行检索。你会发现，许多你所想到的需求，其实已经有很多人提前考虑到并开发了解决方案。例如，在 GitHub 上，关于 Zotero（作为关键词或话题）的插件仓库已有 335 个。其中不乏许多非常有趣的插件，比如 Zotero GPT，它结合了 AI 技术，可以让你直接与 Zotero 中的 PDF 文档进行对话。

Alex 同学提到，有了 cursor，编写「胶水代码」（glue code）变得非常容易。是的，cursor 确实非常好用。大家可以看到，我今天的这段代码就是通过询问 cursor 得到的。这是对话历史，内容不多。它有一个很有趣的功能：我现在的代码仓库文件较少，但如果代码仓库文件较多，且您的问题涉及跨多个代码文件（不仅仅是某个文件的特定片段，而是文件间存在关联），cursor 能够对整个代码仓库进行全面扫描并进行某种形式的「向量化」或「索引化」。之后，在提问时，您可以通过特定按钮或方式，让它能基于对整个代码仓库的理解来回答问题。这种方式的回答效率非常高。相比之下，如果使用传统的 AI，您需要手动复制所有相关的代码片段，粘贴到 AI 工具中提问，然后再将结果复制回来，过程非常繁琐。因此，cursor 确实非常实用。

接下来，「人生无处不经商」同学提问：如果是进行主题检索，如何通过高级检索和构建检索式来确保检索的全面性？

一般情况下，确实应尽量避免单纯依赖主题检索。如果确实需要使用主题检索，那么构建检索式是常用的方法。但问题在于，您对某个主题的理解可能局限于您所使用的关键词，而相关的论文未必会使用完全相同的术语，因此可能导致检索不全。

文献不一定直接涉及该关键词。因此，无论如何，若采用主题检索的方式，都需要做好可能遗漏信息的心理准备。故最佳方式仍是明确该主题所属的学科。如果一级学科范围过大，可以将其细分为二级学科、三级学科等，再进行检索。当然，这仍需根据具体的使用场景而定。例如，若仅为撰写论文中的某个注释而查找特定主题，确实可以采用此种检索方式。此外，目前有一些新兴的 AI 工具可供检索，但由于我个人没有撰写论文的经验，对此方面了解可能不多，可以咨询其他同学是否有相关经验。因为有些工具在实际操作中与理论介绍确实存在差异，因此需要根据您的实际情况灵活调整。

但无论如何，出发点仍应围绕我们课程中提到的三个要点：

首先是构建「全局认识」，并检查是否忽略了关键信息。

其次，如果「全局认识」范围较广，思考「最小全局认识」是否具有代表性。

再次，「交叉验证」是否执行到位。例如，在一个网站进行了主题检索后，可以更换数据库进行新的主题检索，然后对两次结果进行交叉验证，比较哪个网站的结果更丰富。如果结果数量差异显著，便可按图索骥，寻找蛛丝马迹，推演并设法确定信息的边界。

最后是「有趣度」，即所发现的信息是否是他人未曾留意之处，从而使您的「套利点」更多。大致如此。

### 06

接下来，我们开始讨论基础作业。以信息处理为例，首先，在处理任何信息时，比如面对一系列文献，你最初可能会面对从几十篇到上千篇不等的文献量。此时，你会进行一些特定的假设，例如，你需要排除那些确实没有他人引用的文献，并采取诸如此类的筛选手段。这些其实都是你从课程中习得的直觉和有效方法。这同样是信息分析中至关重要的环节，它要求你关注核心信息。

这也是我们与所谓的模型（AI 模型）之间的区别所在。相当于你在受限制的条件下 —— 无论搜索资料还是完成作业，时间总是有限的 —— 来解决问题。大家需要深刻认识到这一点：你总是在有限条件下寻求解决方案。否则，如果你拥有无限的时间进行信息分析，你当然可以逐一查阅所有资料。但现实中永远存在时间限制，你并没有那么多时间。因此，必须做出假设。这些假设可能正确，也可能错误。如果错误的假设体现在作业中，我们便能发现并帮助你纠正。这也是记录（学习过程或作业反馈）的一个重要意义所在。

此外，你可能会发现，在某些领域，并没有大量经过严格审查的论文期刊可供参考。在这种情况下，你首先能做的就是与领域内的专家（人）进行对齐。以语言模型领域为例，大部分的鉴赏力或品味（taste）源于人创作的作品，而人（专家）可以帮助你筛选信息。此时，与其阅读例如像所谓「中文圈顶流科技媒体」（如机器之心）上关于语言模型的文章，不如去关注领域内专家的见解。

关于获取前沿信息，除了传统的论文，还有一些其他途径。首先，发言者提到，不必过于关注那些营销性质的推文，重点应在于那些真正在特定领域产出实际作品的专家。如果涉及直接的付费获取信息，或者信息交流的形式并非传统的论文，那么可以考虑以下几种方式。

例如，可以关注专家的播客对谈。诸如大型语言模型等工具的应用，使得我们进入信息时代后，可以将播客内容转换成文字，然后利用大型语言模型进行总结。这意味着我们拥有了批量处理 500 篇、100 篇甚至 1000 篇播客「文章」（指播客转录稿）的可能性。这在以往单靠阅读论文是无法实现的，因为一个人不可能听完 1000 期播客，但现在技术上能够做到。这是一个非常有趣的获取信息的方法。

其次是推特（Twitter），现在称为 X 平台。在这些平台上，可以看到前辈专家们互相辩论，指出对方言论的不足之处，这是一种非常独特的信息来源。

最后提及的是 Hacker News。对于不了解的听众，Hacker News 是一个非常有趣的国外平台，由 YC（Y Combinator）创办。用户可以将自己的文章或发现的链接提交上去，其他人会对其进行投票。它在一定程度上代表了硅谷及科技从业者日常关注的文章和相关内容。任何被高票推举到首页的文章，通常都会有相应的讨论区，大家会在里面进行深入评论（所谓「睿评」），探讨其价值和不足。在此，发言者特别强调评论区的重要性：评论区代表了社区对发布内容的集体意见，无论是正面还是负面，它反映了社区的品味或形成的共识。与这种共识对齐，或将其作为进行信息分析时的参照假设，是一个极其重要的信息源头。

Hacker News 作为一个新闻聚合和讨论网站，其他网站是否有类似的机制？发言者回应，类似的机制确实存在。例如 OpenReview 平台，这是一个在人工智能（AI）等领域的学术会议中被广泛采用的系统，它提供一个公开的场所，让研究者们进行类似于同行评审的公开辩论或审稿工作。

这些文章，例如我随便打开一个会议（conference）的页面 —— 具体是哪个会议并不重要 —— 点开之后，通常会直接看到评审意见，说明某篇论文为何被接收或被拒稿。这实际上反映了审稿人的学术品味或判断标准，有时这些标准差异可能很大，同时也体现了学术品味上的某种倾向性或差异性。当你在未来某个阶段，需要提炼单篇论文的价值时，可能不清楚其研究背景，也无法准确判断其优劣，因为你尚未形成相应的学术鉴赏力。此时，专家的评审意见至少能提供一个评判标准。无论评审意见的结论如何，它至少指出了具体问题所在，让你能够据此进行对比分析，获得一个客观参照，而不是完全依赖闭门造车式的思考。这一点非常重要。因此，这些内容可以称之为「评论」，这里的「评论」是广义的，希望大家能理解其含义。

### 07

回到计算机领域，与传统文献研读或以期刊为主的学术领域相比，计算机领域更看重会议（conference）。也就是说，这类学术会议以前可能每两年举办一次，现在很多都是每年举办。会议为大家提供了交流平台，让不同研究者在该领域碰撞出新的观点并发表文章，这非常重要。这对于我们理解不同领域的信息交流方式也具有启发意义。如果我们当前所采用的某个领域的信息交换形式，其信息更新速度不够快，那么可以借鉴计算机领域的做法。在计算机领域，会议是研究者们经常关注的场合，也是他们进行学术成果交流的重要平台。因此，会议这种形式、其组织结构以及由此产生的信息，包括其衍生的各个组成部分，都是我们需要重点关注和把握的内容。

举例来说，如果目标人物是 GitHub 上的程序员，我们可以尝试从其代码提交（Commit）记录中找到联系方式。具体操作如下：首先，将目标人物参与的任何一个 GitHub 仓库（例如名为「defy」的仓库）克隆到本地。然后，通过命令行进入该仓库的目录，执行 `git log` 命令。此时，便能看到代码提交者及其邮箱地址。当然，如果提交者不希望被轻易找到，可能会使用 GitHub 提供的隐私邮箱（通常格式为 `xxx@users.noreply.github.com`），但也可能直接使用其真实邮箱。实际上，在提交代码时，这些元数据就已经被嵌入到 Commit 记录中了。也就是说，该项目所有参与者的联系方式（如果他们提交过代码并公开了邮箱）都可能通过这种方式被获取。

这种方法与寻找非程序员作者有何关联呢？即使目标人物的主要身份不是程序员，但他若曾在 GitHub 上参与过任何开源项目（即便未直接公开其邮箱），其邮箱信息也可能隐藏在项目的提交记录中。这背后的逻辑是：如果作者公开了代码，其邮箱很大概率会被嵌入 GitHub 的 Commit Log 中。这是我们基于信息行为推导出的一个假设性结论，当然具体情况因人而异。

Zotero 7 主要面向苹果设备，其特点在于力求实现原生体验，而非一个经过简单移植或兼容性较差的应用程序。但 Zotero 运行卡顿的核心原因在于其实现方式。Zotero 使用 SQLite 数据库进行数据存储，该数据库读取性能尚可，但写入性能相对较弱。大家如果在电脑上查看 Zotero 的数据文件，可以看到其数据库文件（database）实际上直接以 SQLite 数据库的形式存储在本地，用于存放所有信息。

因此，如果您非常在意应用的打开性能，我个人推荐使用「群组」（Groups）功能来分流部分信息。例如，当您进行文献的批量导入时，可以将这些结果导入到专门的群组中，而不是直接放入「我的文库」（My Library）。这样做可以确保在打开主文库时，应用不会因数据量过大而卡顿。您最初可能习惯于将所有文献都导入「我的文库」，但日积月累之下，条目数量可能迅速达到例如两万多条。此时，应用首次打开的速度会显著变慢，进而影响您的整体使用流畅度和「心流」体验。

此外，这种方式也有利于资料的整理。例如，我个人也会将不同类型的资料分门别类地存放在不同的文件夹（群组）中，包括撰写文献时参考的资料、图表数据或图片素材等。实际上，这些也并非我全部的资料库内容，因为我并没有将所有的群组都同步到本地设备。这样做的好处是能够「卸载」（或分流）一部分信息，减轻本地存储和运行压力。而且您也不必担心原始数据不一致或丢失的问题，因为 Zotero 支持将条目（包括附件）无损地在不同群组间迁移，或从云端完整同步到本地。因此，在数据量较大时，适当地通过群组功能「卸载」或分流数据，能显著提升使用体验。这是一个非常实用的小技巧。

关于插件方面，我个人目前并没有发现哪些插件是「非装不可」的。当然，像一些便捷获取文献 DOI 的插件可能比较重要，但它们也尚未达到「非装不可」的程度。相比之下，对于许多用户而言，PDF 文献翻译插件的重要性可能更高一些，因为这能帮助阅读外文文献。

接下来，我们回到数据管理的角度。我最大的建议是，当您导入任何数据入库时，至少要确保满足以下两个条件之一：要么该条目本身拥有完整的元数据 —— 例如，我导入一本书（如《被讨厌的勇气》），其元数据非常齐全；要么它拥有一个唯一的标识符，例如书籍的 ISBN 或论文的 DOI。为什么强调这点呢？因为有了这些标识符，当您未来再次遇到相同条目时，系统就能进行去重处理。如此一来，即使您之前导入的条目在格式上有些许瑕疵，也无伤大雅。这一点非常重要。如果您导入的条目没有 DOI，后续进行去重就会非常麻烦。

因此，有时我会这样做：如果您想查找没有 DOI 的条目，您甚至可以设置一个搜索条件，例如创建一个名为「无坐标论文」的条目类型 —— 我这个设计可能比较复杂 —— 但其主旨就是筛选出那些没有 DOI（即没有唯一标识符）的论文。目前，我的文献库里有 529 篇这类文章。至少我知道它们的存在，您可以有针对性地去处理，当然也可以暂时不处理。它就是把那些缺少 DOI 字段的条目筛选出来。

这就引申出一个重要的技巧：在使用或管理文献库时，这类需要维护的清单应尽可能实现自动化，而非手动管理。您不应该手动创建一个名为「无 DOI」的分类（或文件夹），然后将没有 DOI 的条目手动拖进去。这种做法是绝对不可取的。因为您很可能会忘记这个分类的存在，或者忘记更新它。这也揭示了知识管理中一个重要原则，可能大家对此认识尚浅：人的认知能力是有限的。也就是说，您在同一时间通常只能专注于处理一个条目；当您转而处理其他事情时，很容易忘记之前的事情。因此，这种需要由机器（或系统）来自动维护的列表，千万不要依赖人工操作。

在这种情况下，你很可能会遇到困境。这就像我上次提到的一个由人工智能生成的图像网站（我不确定现在是否还能打开）。要理解这个网站的运作，首先需要明白一个重要概念，即「色调的复杂度」。

现在，我们设想一个场景：假设你正在本地管理图书，会遇到什么问题呢？请看这样一张图所展示的情景：如果你现在正在右侧界面管理元数据（metadata）或操作任何类似的软件，那么对这些条目的修改，要么通过机器自动处理，要么通过人工操作。然而，手动操作在某些情况下是行不通的。例如，你可能希望对文件进行排序。当前，这些文件已按名称排序，这是因为遵循了字符串的排序规则。但此时，如果你想按时间排序，就无法直接操作，除非你手动为每一个文件进行重命名以反映时间信息。

这一点非常重要：如果你要进行任何一项操作，其工作量都会与你当前拥有的条目总数相关联。也就是说，假设你通过文件系统来管理，这里有 126 个文件，那么任何操作（比如为了排序而检查信息）都可能需要遍历所有文件，这在文件数量多时是不现实的。

相比之下，如果你使用任何专业的管理软件（无论是像 Amazon 云服务还是诸如 Zotero 这样的客户端工具），通常只需点击一下，软件就能自动帮你筛选或排序。这是最主要的区别。因此，如果你在工作流程中可能会遇到这类涉及多条目管理和排序的问题，千万不要试图手动操作，因为这种方式是不可持续且难以维护的。

我们再次强调，以时间排序为例，由于文件默认按名称（即字符顺序）排列，若想按时间排序，手动操作将非常困难，除非对每个文件进行重命名。关键在于，任何手动操作的成本都会随着条目总数的增加而急剧上升。若用文件系统管理 126 个文件，每一次需要全局检查的操作都意味着要遍历所有内容，这显然不切实际。然而，在专业的管理软件中（如前述的各类工具），这些操作通常可以轻松完成。

例如 Apple Store 这类应用，其筛选功能实际上也是通过点击自动完成的。这（自动化筛选）是一个非常重要的方面。只要你的日常操作中可能遇到类似需要整理或筛选的问题，就千万不要尝试手动处理，因为手动方式无法持续维护。人的时间有限，手动更新大量数据会耗费巨大的心力，所以绝对不要这样做。

反过来说，这也决定了哪些事情适合用这种自动化或结构化的方式处理：你所构建的整个体系，包括高级搜索和信息调用结构，都必须具有时间上的稳定性。因为一旦结构不稳定，每当数据调整或结构变更，即便一年只修改整理一次个人知识库，假设每次需要花费半天时间，那么一年下来也可能因此浪费至少八个小时。如果你使用这类工具长达八年，那就相当于花费了整整四天的时间在整理这些清单上。但如果你本身的结构比较稳定，就不会出现这个问题。此时，你可以适当牺牲一些表述的灵活性或细节的丰富性，以确保所设计的结构是稳定的。

一般来说，这仍然是一个比较宏观层面的建议。但在实际操作中，你大概率会这样应用：首先，对于那些即用即抛的小型清单，当你对某个主题不再深入研究时就可以直接丢弃，这通常影响不大。其次，另一种可能比较有用的结构是按时间排序的结构。例如，我个人会将一些信息按作者、组织或会议进行分类，这类信息相对稳定，可以每年回顾一次。至于剩下的，则可能是我在特定时间段内感兴趣的某个主题，但这属于即用即抛的性质。也就是说，之前收集的这类信息我不会再刻意维护，没有了就作罢，不必过于在意。我主要关注的是那些关键领域专家的文章。

总而言之，大家可以根据自己的经验去设计适合自己的信息组织模式。但需要注意一点：稳定的结构不应轻易变动；而对于动态变化的结构，则要确保其中的信息是可以随时舍弃的，也就是说，这些信息你可能在不久的将来就不再需要了。

关于 Zotero，当您想到某个条目时便可以回顾，但在多数情况下，有些内容可能一个季度后就不再需要回顾了。基于这种设计，您的知识库结构会相对稳定。但它确实无法涵盖您当前一些临时的知识管理需求。此时，您就需要灵活地创建新的条目或笔记来解决这些临时问题。这大致就是我对 Zotero 的一个补充说明，希望对大家将来使用 Zotero 进行知识管理有所帮助。我的分享就到这里。

在使用 `git clone` 时，如果你需要设置代理，可以通过配置 Git 的代理设置来实现。你可以设置 HTTP 或 HTTPS 代理，具体步骤如下：

\### 设置 HTTP 代理
```bash
git config --global http.proxy http://<代理IP>:<端口>
```

\### 设置 HTTPS 代理
```bash
git config --global https.proxy https://<代理IP>:<端口>
```

如果你希望取消代理设置，可以运行：
```bash
git config --global --unset http.proxy
git config --global --unset https.proxy
```

\### 临时设置代理（仅对当前 `git clone` 有效）
你也可以通过环境变量临时设置代理：
```bash
HTTP_PROXY=http://<代理IP>:<端口> git clone <仓库地址>
```

4、下载终止后的处理措施。

Git Large File Storage (LFS) 是一个用于处理大文件的 Git 扩展。如果你在使用 Git LFS 下载大文件时遇到中断，通常可以通过再次执行 `git lfs pull` 或 `git pull` 命令来重新开始下载流程。

备注：要开代理干其他事情的时候，可以人为的中断下（ctrl+c）。



以下是一些步骤，可以帮助你继续下载被中断的文件：

1、重试拉取命令：

执行 `git lfs pull` 或 `git pull` 来尝试重新开始下载。Git LFS 会尝试从上次中断的地方继续下载。

git lfs pull

或者

git pull

2、增加 Git LFS 的超时时间：

如果你认为下载中断是因为 Git LFS 超时，你可以尝试增加超时设置：

git config lfs.dialtimeout 10

git config lfs.tlstimeout 10

git config lfs.activitytimeout 30

这里的时间是以秒为单位的。调整这些值可能会帮助你避免因网络延迟导致的超时问题。

3、清理 Git LFS 缓存：

有时候，清理 Git LFS 的缓存可以解决下载问题：

git lfs prune

4、查看 Git LFS 日志：

如果上述步骤都不起作用，检查 Git LFS 的日志可能会提供更多关于为什么下载失败的信息：

git lfs logs last

5、手动下载：

如果自动下载一直失败，你可以尝试手动下载问题文件。首先找到文件的 LFS 指针文件，它通常是一个文本文件，里面包含了文件的元数据。然后，你可以使用 `git lfs fetch` 命令和对应的文件指针来手动下载文件。

git lfs fetch --all

或者，单独为特定文件：

git lfs fetch origin <path-to-file>

如果你仍然遇到问题，可能需要查看你的 Git LFS 配置或者联系你的 Git 仓库托管服务的支持团队，以获得更具体的帮助。

当使用 Git LFS 管理的项目有更新时，你通常会按照正常的 Git 工作流程来更新你的本地仓库。这包括 `fetch`、`pull` 或 `checkout` 等命令。Git LFS 会自动处理大文件的下载。

以下是更新到最新数据的一般步骤：

1、获取最新的仓库信息：

首先，你需要获取远程仓库的最新信息。可以使用 `git fetch` 命令来完成这个操作。

git fetch

2、切换到相应的分支：

如果你不在要更新的分支上，使用 `git checkout` 命令切换到正确的分支。

git checkout main

或者切换到你想要更新的任何分支。

3、拉取最新的更新：

使用 `git pull` 命令拉取最新的更新。这个命令会合并远程分支的变更到你的本地分支。

git pull origin main

或者拉取你想要更新的任何分支。

如果项目使用了 Git LFS，并且有 LFS 对象的更新，`git pull` 会自动调用 `git lfs pull` 来下载最新的 LFS 对象。

4、确保 LFS 对象是最新的：

有时候，你可能需要手动触发 LFS 文件的下载，尤其是在有大量 LFS 对象时。你可以使用 `git lfs pull` 来确保所有 LFS 对象都是最新的。

git lfs pull

5、检查 Git LFS 状态：

要检查 Git LFS 管理的文件的状态，你可以使用以下命令：

git lfs ls-files

这个命令会列出所有由 Git LFS 跟踪的文件，以及它们的版本信息。

6、处理可能的合并冲突：

如果在拉取最新的更新时遇到合并冲突，你需要手动解决这些冲突。解决冲突后，提交这些更改以完成合并。

git add .

git commit -m "Resolve merge conflicts"

如果你遇到了下载 LFS 对象时的问题，可以按照之前提到的步骤来检查和解决这些问题。记住，保持 Git 和 Git LFS 的客户端更新到最新版本可以帮助避免兼容性和其他问题。
